## 1. Purpose, authorities, and boundaries

The future system validates the coordinator-owned PROGRAM.md as a plan-integrity input. It parses the canonical five-column slice ledger, computes its dependency graph, checks the status census, proves dynamic F-07 closure and coordinator-declared direct prerequisites, audits the sole stable-promotion seam, and verifies that decision and progress history is append-only against the immutable event base. It emits deterministic JSON, a human fail census, and phase-gating evidence.

Plan integrity is not release readiness. A passing plan-integrity result does not establish implementation, signing, reproducibility, legal distribution, board qualification, physical evidence, installer safety, hardware compatibility, support, release, or DONE. F-07 remains the sole stable-promotion authority, and this design never authorizes a release or changes branch protection.

The human-produced opaque boundary named by PROGRAM.md is outside this design. The future validator receives only externally declared boundary metadata and never reads, traverses, characterizes, builds, or tests any source under that boundary. The external owner token and its distinct shipping-hardware token remain exact prerequisite metadata only; neither is resolved to a path, repository, source, or executable, and any opaque-boundary path is excluded from the agent-operated source universe.

The consumed authorities are the pinned-parent AGENTS.md, the pinned-parent PROGRAM.md, and typed canonical GitHub event, governance, and Git-object metadata. AGENTS.md supplies one-writer, coordinator-only DONE, append-only history, reviewer, and fail-closed rules; it does not supply an exact-base rule. The task assignment and event contract supply the immutable base and parent requirements. PROGRAM.md supplies the ledger, its acceptance section, its policy declaration when added, its status vocabulary, and Sections 18 and 19. The coordinator base is the only acceptance authority unless an owner-ratified FoundationAuthorityUpdate/v1 record is validly supplied.

## 3. Raw-byte and Markdown contract

The validator consumes raw bytes without Markdown rendering, HTML conversion, Unicode normalization, whitespace normalization, line-ending conversion, or reserialization. Every physical line ends in exactly one ASCII LF byte except that the final line may omit LF. Any CR byte, including CRLF, is PI_LINE_ENDING at `PROGRAM.md` in phase `preflight` with exit status 10. UTF-8 is decoded only after the raw line-ending check.

The rejected control set is U+0000 through U+0009, U+000B through U+000C, U+000E through U+001F, and U+007F through U+009F. LF U+000A is the only permitted control character. Tabs, DEL, C1 controls, and CR are therefore never accepted. PI_CONTROL_CHAR reports the byte offset, code point, source path, and phase `preflight`; PI_LINE_ENDING takes precedence for CR. A NUL, invalid UTF-8 sequence, or C1 byte is never interpreted as a delimiter or line boundary.

All structural delimiters are ASCII bytes: `|` U+007C, `-` U+002D, `,` U+002C, and ASCII space U+0020. Fullwidth, confusable, non-ASCII, or normalized delimiter characters are not delimiters. Cell-edge trimming removes ASCII spaces only; it does not remove tabs, non-breaking spaces, or any other character. Every accepted ASCII token is compared byte-for-byte and case-sensitively.

The scanner is a total byte state machine with states `NORMAL`, `FENCE`, `COMMENT`, and `CODE_SPAN`. A fence opener is a physical line whose first byte is ASCII space repeated zero through three times, followed by at least three identical backticks or tildes; its trailing bytes are an opaque info string and the line must have its normal LF termination. A closer uses the same fence character, has at least the opener length, and may have only ASCII spaces after the run before LF. A shorter run or non-space trailing byte is content, not a closer. Fence openers are not nested: an opener-looking line inside `FENCE` is literal content and a target-shaped line there is recorded as a laundering lookalike. EOF in `FENCE` is PI_FENCE_UNTERMINATED at `PROGRAM.md.fence` in phase `preflight` with exit status 10.

An HTML comment starts at the exact byte sequence `<!--` outside `FENCE` and ends at the exact byte sequence `-->` outside `FENCE`; comment state is byte-stream based and may cross physical lines. A second `<!--` in `COMMENT` is PI_COMMENT_NESTED, a `-->` in `NORMAL` is PI_COMMENT_CLOSE, and EOF in `COMMENT` is PI_COMMENT_UNTERMINATED. Each is at `PROGRAM.md.comment` in phase `preflight` with exit status 10. Target-shaped headings, headers, delimiters, and rows inside a comment are recorded as lookalikes and cannot satisfy selection. A fence marker inside a comment is comment content, and a comment marker inside a fence is fence content.

An inline code span outside `FENCE` and `COMMENT` starts with a run of one or more backticks and closes only on the same physical line with a run of exactly the same length. Its content is literal and cannot create a structural heading, table, or comment; if it contains target-shaped material, the scanner records PI_MARKDOWN_LAUNDERED at `PROGRAM.md` in phase `preflight` with exit status 10. An unmatched span is PI_CODE_SPAN_UNTERMINATED at `PROGRAM.md.literal` in the same phase. Leading indentation of one through three spaces makes a target-shaped line nonstructural and records a lookalike; four or more spaces is code content and records a lookalike. Tabs are rejected before indentation classification. A structural heading or table line must begin at byte column zero and have no trailing spaces.

The parser selects exactly one structural raw line `## 12. Slice ledger` and exactly one structural raw line `### 12.1 Foundation slice acceptance`, with those exact bytes and no trailing spaces. The Section 12 region starts at the `#` byte of the selected `## 12. Slice ledger` line and ends immediately before the next exact structural `## ` heading, or at EOF. Every raw byte in that region is scanned for duplicate or laundered target material. A duplicate structural heading, duplicate table candidate, or lookalike paired with a missing real target is PI_LEDGER_TABLE at `PROGRAM.md` in phase `ledger_parse` with exit status 10.

The Section 12.1 acceptance region starts at its exact structural heading and contains exactly one contiguous acceptance table with the exact three-column header `| Slice | Required executable artifacts | Hard rejection conditions |`, one delimiter row with three cells containing exactly `---`, and the six foundation rows F-02 through F-07 from the coordinator base authority. Its table ends at the first blank LF line after the contiguous table. Text between that table and the ledger is prose and must not contain another ledger header or table candidate, whether rendered, fenced, commented, code-spanned, or HTML-shaped. A missing, duplicate, or laundered acceptance table is PI_ACCEPTANCE_AUTHORITY at `authority.section12_1` in phase `authority` with exit status 14.

The ledger is the only table in the Section 12 region with the exact structural header `| ID | Repository | Deliverable | Depends on | Status |`. The selected ledger begins at that exact header, includes its exact delimiter row and at least one data row, and ends at the first blank LF line or exact structural heading after the contiguous data rows; every intervening pipe-prefixed line is part of the table and must parse. There must be exactly one such header, exactly one five-column ledger table, and no duplicate exact heading, duplicate table, table-shaped lookalike, or alternate rendering of it anywhere in the raw Section 12 region. An HTML table, rendered HTML, Markdown AST, code-fence table, HTML-comment table, or second table cannot satisfy selection; a fake target in any of those forms is evidence of laundering and fails PI_LEDGER_TABLE.

A five-column ledger row has exactly six ASCII `|` delimiters: a leading delimiter, four internal delimiters, and a trailing delimiter, yielding five cells. “Six delimiters” is the precise boundary rule; five delimiters is malformed. The header, delimiter row, and every data row use this same six-delimiter rule. A cell cannot contain a pipe, including a backslash-escaped pipe or a pipe inside a code span; multiline cells are forbidden because each row is exactly one physical source line.

The ledger header cells must be exactly `ID`, `Repository`, `Deliverable`, `Depends on`, and `Status` after ASCII-space edge trimming. The delimiter row must contain exactly five cells, each exactly `---` after ASCII-space edge trimming. Any missing, duplicated, or lookalike header, delimiter, or data table is PI_LEDGER_TABLE at `PROGRAM.md` in phase `ledger_parse` with exit status 10. A pipe-prefixed malformed line within the selected table is PI_ROW_SHAPE, not ignored prose.

Each data row has exactly five non-empty cells in the same order. The row record retains exact raw row bytes, exact source line, zero-based row index, byte start and end offsets, and parsed fields; every downstream phase consumes that record and never reparses the source. The source line number is one-based and counts physical LF-terminated lines from the first byte; the final unterminated line still has one line number. A ledger data row index is zero-based from the first data row after the delimiter row.

The ID grammar is ASCII and case-sensitive: `(B|F|G|I|K|P|Q)-[0-9]{2}`. The set of IDs is derived from the rows and never hard-coded. Status is exactly one of `DONE`, `IN PROGRESS`, `REVIEW`, `TODO`, or `HUMAN-ONLY BLOCKED`; an unknown status is PI_STATUS_UNKNOWN at the concrete rendered path `ledger.rows[0].status` when the first row is mutated, or the same renderer with the actual zero-based index in a generated fixture, in phase `ledger_parse` with exit status 10. A malformed ID prefix, width, separator, Unicode lookalike, or normalization is PI_ID_SYNTAX at `ledger.rows[0].id` for that same first-row fixture and the actual indexed renderer otherwise, in phase `ledger_parse` with exit status 10.

The dependency grammar is closed and typed. The cell is either the exact ASCII token `none` or a non-empty sequence separated only by the exact two-byte delimiter `, `; no leading or trailing comma, extra space, missing space, empty token, tab, or other separator is accepted. Each token is exactly one of `id = [A-Z]-[0-9]{2}`, `external_owner = human m1n1 owner`, or `external_shipping_hardware = shipping hardware`. The two external literals are the complete allowlist of non-ID tokens: the owner token is an opaque human prerequisite bounded by the named m1n1-omarchy boundary, and the shipping-hardware token is a distinct physical-availability prerequisite; neither creates an internal edge, is resolved, or is interchangeable with the other. The pinned base recomputation must find exactly six `external_owner` occurrences and exactly two `external_shipping_hardware` occurrences, on B-01, B-02, B-05, B-06, B-07, B-08 and K-06, B-08 respectively, for eight external prerequisites and 134 internal edges. An ID-shaped token is admitted to graph checking and becomes PI_DEP_UNKNOWN if absent from the parsed row-ID set, so `Z-99` is a graph unknown rather than a parser error. A non-ID token not equal byte-for-byte to one of the two external literals is PI_DEP_SYNTAX at `ledger.rows[0].depends` for the first-row fixture and the actual indexed renderer otherwise, in phase `ledger_parse` with exit status 10; it is never silently classified as an external prerequisite. An empty dependency cell after ASCII-space edge trimming is PI_ROW_SHAPE; a leading, trailing, or doubled comma that creates an empty token is PI_DEP_EMPTY; doubled spaces, tabs, or another separator are PI_DEP_SYNTAX; and `none` combined with any other token is PI_DEP_SYNTAX. The parser retains `token_kind`, exact token bytes, and source ordinal for every token. Token order is significant: for a row already present in the pinned base, the candidate sequence must equal the pinned sequence after removing deleted tokens and appending newly added tokens in ascending raw-token-byte order; for a new row, all internal ID tokens are sorted by ascending ASCII ID, followed by external tokens in this fixed typed order: `shipping hardware`, then `human m1n1 owner`. This base-relative rule preserves the non-lexical coordinator order in F-07 while making every candidate order deterministic. A valid-token reorder is PI_DEP_ORDER at `ledger.rows[0].depends` for the first-row fixture or the actual indexed renderer otherwise, in phase `graph` with exit status 11. All parser classifications use the stated path, phase, and exit status.

The graph phase, not the parser phase, reports repeated dependency tokens as PI_DEP_DUPLICATE at `ledger.rows[0].depends` for the first-row fixture and the actual indexed renderer otherwise, in phase `graph` with exit status 11. This fixes the duplicate-token phase boundary: lexical separator faults are parser failures, while exact repeated tokens are graph failures. Unknown graph IDs are PI_DEP_UNKNOWN, self-edges are PI_DEP_SELF, and cycles are PI_DEP_CYCLE, each at the exact rendered row/field or `graph.cycle` path in phase `graph` with exit status 11.

## 4. Coordinator-owned promotion policy and monotonic evolution

There is no promotion mode switch. Every invocation has the same promotion-policy precondition, and no invocation can return PI_OK until the required PROGRAM policy declaration exists and parses exactly. Until the declaration exists and parses exactly in the candidate PROGRAM, the policy phase is PI_POLICY_UNDECLARED at `policy.program_integrity` in phase `policy` with exit status 12, regardless of whether the invocation is local, pull-request, merge-queue, direct-push, or post-merge; an earlier trust or input failure may still control the overall primary result.

The minimum coordinator-owned declaration is an append-only policy history under Section 12 with this exact structural heading and exact record grammar. The code block specifies source bytes; its backticks are not part of PROGRAM.md.

```text
### 12.2 Program-integrity policy history

Program-integrity policy version: 1
Policy document ID: sha256:<64 lowercase hex>
F-07 mandatory direct prerequisites: F-05, P-03, P-05, I-09, B-04
Q cohort rows: ID matches Q-[0-9]{2} and Deliverable begins with the exact case-sensitive verb Certify followed by one ASCII space.
Allowed statuses: DONE, IN PROGRESS, REVIEW, TODO, HUMAN-ONLY BLOCKED
F-07 closure rule: Every parsed ledger ID is in `DepClosure(F-07)` under the named dependency relation `R_dep`, whose edges point from each consumer to each prerequisite.
Acceptance authority: Section 12.1 rows F-02 through F-07 are pinned to coordinator base bytes.
Rejection behavior: Any unmet required condition returns FAIL with a nonzero exit and no PASS artifact.
```

The raw declaration is one exact heading line with LF, one blank LF, and one or more exact eight-line records, with one blank LF between records; the final record ends immediately before the first exact structural `## ` heading. The heading occurs exactly once outside fences, comments, and code spans, and no target-shaped heading or record occurs elsewhere in Section 12. The version is a positive ASCII decimal without leading zeroes, versions are unique and strictly increasing, and the direct-prerequisite value is a non-empty exact ASCII ID list separated by `, ` with no duplicate IDs; each ID must exist in the same ledger. The Q, status, closure, acceptance, and rejection lines are exact, including capitalization, punctuation, and final periods. The `Policy document ID` is not self-referential: it is `sha256:` plus 64 lowercase hex characters over the exact UTF-8 bytes of the other seven record lines from the version line through the rejection line, including each LF and excluding the ID line. The policy-history byte digest is SHA-256 over the exact bytes from the heading through the final record LF, including blank separators.

Each policy record expands to a canonical semantic map with these stable item IDs and exact values: `F07.DIRECT.<ID>` for every direct prerequisite, `Q.COHORT.RULE` for the exact Q line, `Q.COHORT.<ID>` for every derived qualifying Q row, `LEDGER.STATUS.VOCABULARY` for the exact status line, `F07.CLOSURE.RULE` for the exact closure line, `AUTHORITY.SECTION12_1` for the exact acceptance line, and `REJECTION.FAIL_CLOSED` for the exact rejection line. The semantic map also records source record version, source byte range, item byte digest, and consumer set. A policy document ID is recomputed from its exact bytes and is never accepted merely because its syntax is valid.

The monotonic comparison is a deterministic superset/diff algorithm. Parse the complete base and candidate histories from immutable PROGRAM bytes; require the base history to be an exact raw-byte prefix ending at a complete record boundary, require unchanged history to retain every raw byte, and select the highest version as effective. Build `B` and `C` as maps from semantic item ID to exact canonical value bytes. Compute `removed = {id in B where id is absent from C or C[id] != B[id]}`, `added = {id in C where id is absent from B or C[id] != B[id]}`, and `retained = B - removed`; iterate each set in ascending ASCII item-ID order. A candidate with `removed` empty and `added` empty may retain the same version; any candidate with additions or a new effective record must have a strictly higher version. Every retained value must be byte-identical. A changed value is treated as removal plus addition, never as an implicit strengthening. The effective policy is derived from the candidate ledger and its exact policy bytes, not from a duplicated validator constant: direct item IDs are the literal policy list, qualifying Q items are regenerated from the literal Q rule, and the report records the derived item census and source row digests.

Direct prerequisites and Q cohort membership are set-valued requirements, so `C` must contain every `F07.DIRECT.<ID>` and `Q.COHORT.<ID>` present in `B`; adding a direct prerequisite or qualifying Q row is a monotonic addition. The Q rule itself is an exact retained value, so changing the verb, case, whitespace, predicate, or interpretation is a removal. Status vocabulary, closure rule, acceptance condition, and rejection behavior are exact retained requirements; they cannot be removed, shortened, replaced, or made less strict by editing text, changing a version, changing a Deliverable verb, or relying on a candidate-derived count. There is no silent Deliverable-verb shrinkage.

If `removed` is non-empty, the candidate must supply exactly one owner-authorized `PolicyRemoval/v1` record for that comparison. Without it, the result is PI_POLICY_DOWNGRADE at `policy.diff.removed["F07.DIRECT.P-03"]` for the P-03 fixture, or the exact quoted-item renderer for the actual first removed item, in phase `policy` with exit status 12. An authorization record cannot hide an additional removed item, preserve a changed item under the old ID, authorize a changed acceptance table, or authorize an item outside the computed set; those cases remain failures. If a record is present when `removed` is empty, the result is PI_POLICY_REMOVAL_UNEXPECTED at `policy_removal` in phase `policy` with exit status 12. A policy version, changed Deliverable verb, changed Q cohort, or changed policy prose never bypasses this comparison.

`PolicyRemoval/v1` is an exact UTF-8 record with LF-terminated ASCII field names in this order and no other fields: `PolicyRemoval/v1`, `repository=omarchy-silicon/omarchy-apple-platform`, `pull_request_number=<positive decimal or null>`, `event_id=<lowercase GitHub delivery UUID>`, `run_id=<positive GitHub Actions run ID>`, `base_commit_oid=<40 lowercase hex>`, `candidate_commit_oid=<40 lowercase hex>`, `candidate_ref=<exact canonical immutable ref>`, `base_program_sha256=sha256:<64 lowercase hex>`, `candidate_program_sha256=sha256:<64 lowercase hex>`, `base_authority_region_sha256=sha256:<64 lowercase hex>`, `candidate_authority_region_sha256=sha256:<64 lowercase hex>`, `base_authority_table_sha256=sha256:<64 lowercase hex>`, `candidate_authority_table_sha256=sha256:<64 lowercase hex>`, `previous_policy_document_id=sha256:<64 lowercase hex>`, `previous_policy_sha256=sha256:<64 lowercase hex>`, `previous_version=<positive decimal>`, `new_policy_document_id=sha256:<64 lowercase hex>`, `new_policy_sha256=sha256:<64 lowercase hex>`, `new_version=<positive decimal>`, `removed_semantic_item_ids=<sorted comma-space list of exact item IDs>`, `reason_b64=<RFC4648 base64 with padding>`, `actor=<canonical GitHub login or owner-team identity>`, `role=<coordinator|repository-owner>`, `context_b64=<RFC4648 base64 with padding>`, `timestamp=<UTC RFC3339 second precision ending Z>`, `expiry=<UTC RFC3339 second precision ending Z>`, `nonce=<lowercase UUID>`, `replay_identity=<lowercase UUID>`, `decision_log_row_b64=<RFC4648 base64 with padding>`, `decision_log_row_sha256=sha256:<64 lowercase hex>`, `affected_consumers=<sorted comma-space list of exact consumer IDs>`, and `signature_b64=<RFC4648 base64 with padding>`. `candidate_ref` is `refs/pull/N/merge` for a pull request, `refs/heads/main` for a direct push, and the exact immutable merge-group candidate ref for a queue event. The pull-request candidate commit is the immutable merge commit at `refs/pull/N/merge`; its first and second parents are the event base and PR head respectively. The signature is Ed25519 over all preceding record bytes including their LF; its public key and actor-to-role binding come only from the trusted governance authority.

The removal validator recomputes every policy, PROGRAM, authority-region, and authority-table digest, verifies repository, pull-request, event, run, base commit, candidate commit, candidate ref, and current invocation equality, checks previous and new versions, requires `removed_semantic_item_ids` to equal the computed `removed` set exactly, decodes the reason/context and decision-log row, recomputes the row digest, and requires that exact raw row including its LF to be a newly appended Section 18 row in the candidate. It requires an allowed actor and role, `timestamp <= current trusted time < expiry`, expiry no more than 30 days after timestamp, and an affected-consumer set equal to the consumers of all removed items. If the computed removal set is empty, any present record is PI_POLICY_REMOVAL_UNEXPECTED before record parsing; if the set is non-empty, the record decision order is structural/signature/key/set/version/digest/row/field validation, then invocation binding, then freshness, then replay. Structural or cryptographic errors are PI_POLICY_REMOVAL_INVALID at `policy_removal` in phase `policy` with exit status 12. A cryptographically valid record whose repository/event/run/ref/commit/digest binding differs from the current invocation is PI_POLICY_REMOVAL_TRANSPLANT at `policy_removal.binding` in phase `policy` with exit status 12. A bound record whose timestamp is in the future, expiry is at or before trusted time, or freshness window exceeds 30 days is PI_POLICY_REMOVAL_STALE at `policy_removal.freshness` in phase `policy` with exit status 12. A bound, fresh record whose nonce or replay identity is already consumed is PI_POLICY_REMOVAL_REPLAY at `policy_removal.replay_identity` in phase `policy` with exit status 12. These predicates are mutually exclusive and evaluated in that order; stale is never invalid and replay is never stale. The report records previous/new document IDs, versions, item IDs, record digest, decision-log row digest, actor, role, context digest, freshness, nonce, replay identity, and affected consumers without exposing secret or raw reason bytes.

The current pinned base has no policy history, so its policy byte sequence is empty and its honest policy result is PI_POLICY_UNDECLARED. The context_b64 field decodes to the exact UTF-8 JCS object GovernanceAuthorizationContext/v1 with keys repository, pull_request_number, event_id, run_id, base_commit_oid, candidate_commit_oid, candidate_ref, base_program_sha256, candidate_program_sha256, base_authority_region_sha256, candidate_authority_region_sha256, base_authority_table_sha256, candidate_authority_table_sha256, actor, role, and affected_consumers. ## 6. Graph, closure, and phase gating

After a complete ledger parse and authority check, graph checks run in this exact order: duplicate IDs, unknown graph dependencies, repeated dependency tokens, dependency-token order, self-edges, and cycles. A graph error prevents topological traversal, status census, F-07 closure, and F-07 direct-edge evaluation from claiming success. The dependency relation is named `R_dep`: `(consumer, prerequisite)` exists exactly once for every internal ID token in that consumer row. Kahn’s presentation relation is `R_kahn`, the reverse edge `(prerequisite, consumer)`; it uses a min-heap ordered by canonical ASCII ID, so dependencies precede consumers deterministically. A cycle witness follows lexicographically sorted `R_dep` prerequisite edges from the smallest unvisited node and rotates the closed witness to its smallest first ID. External tokens are typed prerequisites, never vertices or edges.

F-07 policy checks require exactly one F-07 row. The exact closure relation is `DepClosure(F-07)`, the least fixed point of `S0={F-07}` and `S(n+1)=S(n) union {p | (v,p) in R_dep for v in S(n)}`; the implementation recursively visits `dependencies[v]` in retained token order until no new ID exists. It may produce the same set by traversing reverse `R_kahn` edges, but it must not use forward consumer reachability from F-07. The report records `closure_relation=R_dep`, `seed=F-07`, visit order, sorted member IDs, and `member_count`; the independently recomputed pinned base must be 52/52, while literal forward `R_kahn` reachability is intentionally recorded as 1/52 and is never used for acceptance. The closure must equal the complete parsed ID set. A missing ID is PI_F07_CLOSURE at `policy.f07.closure["P-08"]` for the P-08 fixture, or the exact quoted-ID renderer for the actual missing ID, in phase `promotion` with exit status 12. The closure check is dynamic and automatically includes a newly added ledger ID when that ID is connected to F-07.

The direct-edge set is the union of exact IDs parsed from the effective policy record and the non-empty derived Q cohort set. The effective policy list is the only authority for the five mandatory non-Q items; Q membership is regenerated from the exact Q predicate and sorted by row ID. Each required edge must occur literally in F-07’s dependency token sequence, and the sequence must preserve the canonical base-relative dependency order described in Section 3. ## 7. Canonical SourceManifest/v2 and SourceBundle/v2

The trusted host adapter produces SourceManifest/v2 and SourceBundle/v2 from the immutable candidate commit and complete root tree. These are canonical byte formats, not descriptive labels. The manifest is UTF-8 bytes whose ASCII grammar is exact, has no BOM, uses one LF after every line, and has no final digest line omitted. Header and field names are ASCII and case-sensitive. In the grammar block, each displayed `\t` denotes one ASCII HTAB byte U+0009, not two backslash characters; a literal backslash followed by `t` is invalid. The manifest contains every tracked leaf returned by `git ls-tree -r -z --full-tree <candidate_commit>` in raw path-byte order, not merely `src/release/**`, and is exactly:

```text
SourceManifest/v2
commit_oid=<40 lowercase hex>
root_tree_oid=<40 lowercase hex>
entry_count=<positive ASCII decimal or 0>
total_size=<ASCII decimal>
E\t<base64url-no-pad path bytes>\t<100644|100755|120000|160000>\t<regular|symlink|submodule>\t<ASCII decimal length>\tsha256:<64 lowercase hex>\t<40 lowercase hex blob oid or 40 lowercase hex gitlink oid>
manifest_sha256=sha256:<64 lowercase hex>
```

The `manifest_sha256` value is the SHA-256 of the exact manifest preimage from byte zero through the LF ending the last `E` line, excluding the digest line itself. The entry count and total size are recomputed; no duplicate header, unknown key, blank line, extra field, missing field, or alternate encoding is accepted. `entry_count` is at most 10,000, `total_size` and every regular-file length are at most 8,388,608 bytes, a path is at most 4,096 raw bytes and at most 64 components, and the manifest is at most 56,030,250 bytes under the stated maxima. The bound is the exact worst-case sum `162 + 10,000 * 5,603 + 88 = 56,030,250`, where a 4,096-byte path encodes to 5,462 unpadded base64url bytes, the longest allowed entry is `160000\tsubmodule`, and the final 88-byte digest line is included. A zero-entry manifest is valid as a source object but cannot satisfy the stable-writer seam, which reports PI_STABLE_WRITER_SEAM_ABSENT.

The path token decodes with RFC 4648 base64url without padding to raw path bytes. Those bytes must be valid UTF-8, contain no NUL, backslash, colon, control, non-breaking space, or invalid sequence, be relative, have no leading slash, trailing slash, empty component, `.` component, or `..` component, and use at most 64 components. Raw path bytes are the identity and are sorted strictly ascending; a second entry with the same raw path or the same path after applying Unicode NFKC to each component and Unicode casefold to each resulting component is PI_SOURCE_ENTRY. The latter normalized key is the complete component-alias relation; no filesystem lookup or platform-dependent alias resolution is permitted. Every entry has one allowed mode/type pair: `100644` or `100755` with `regular`, `120000` with `symlink`, or `160000` with `submodule`; the Git tree type, stored bytes, length, and digest must agree. Symlinks are never followed, submodules are never cloned, directories are not fabricated as entries, executable modes are retained for audit, and any other type/mode, traversal, absolute path, alias, or duplicate is PI_SOURCE_ENTRY at `source.manifest.entries[0]` for the first-entry fixture and the actual indexed renderer otherwise, in phase `source_bundle` with exit status 14. A symlink, submodule, binary regular file, source-like file with an unsupported language, executable script, generated/copied source, or helper path cannot be hidden by a manifest scope; if it is a potential publisher the stable-writer audit rejects it before promotion.

SourceBundle/v2 is a binary preimage with no text decoding. Bytes 0 through 15 are exactly the 15 ASCII bytes `SOURCE-BUNDLE/2` followed by one NUL byte. Bytes 16 through 19 are an unsigned big-endian u32 entry count. For each manifest entry in manifest order, the bundle contains an unsigned big-endian u32 path-byte length, exactly that many decoded path bytes, an unsigned big-endian u32 mode value, one byte type value `0x01` for regular, `0x02` for symlink, or `0x03` for submodule, an unsigned big-endian u64 content length, exactly that many content bytes, and 32 raw digest bytes equal to the manifest content SHA-256. For regular and symlink entries, content bytes are the exact Git blob bytes; for a submodule, content bytes are exactly the 20 raw bytes of its gitlink object ID and the manifest object_oid is that same gitlink ID. The fixed record overhead excluding path and content is exactly 49 bytes: 4 path-length bytes, 4 mode bytes, 1 type byte, 8 content-length bytes, and 32 digest bytes. There is no padding, terminator, footer, alternate integer width, or digest alias. A candidate accepted by the stable-writer phase must contain only regular `100644` or `100755` entries; symlink and submodule records are represented for deterministic rejection and never dereferenced. The bundle digest is SHA-256 over every bundle byte from offset zero through EOF, and the maximum encoded bundle size is exactly `16 + 4 + 10,000 * (4 + 4,096 + 4 + 1 + 8 + 32) + 8,388,608 = 49,838,628` bytes; any larger or arithmetic-overflowing input is PI_INPUT_TOO_LARGE at `invocation.inputs` in phase `preflight` with exit status 10.
The manifest-to-bundle relation is exact: counts, order, decoded path bytes, mode, type, length, content digest, and content bytes must agree one-for-one; the bundle has no omitted, added, reordered, duplicated, truncated, or trailing record. Every SourceBundle framing, count, record, order, trailing-byte, or manifest relation violation is PI_SOURCE_BINDING at `source.bundle`, while its detail and evidence carry the first offending record index; header faults use index 0 and trailing faults use the entry-count boundary. The four-byte bundle mode is the unsigned big-endian numeric POSIX mode (`0o100644`, `0o100755`, `0o120000`, or `0o160000`), not the decimal text spelling. For each entry the adapter independently verifies Git commit OID, root-tree OID, path bytes, mode, type, blob or gitlink OID, stored byte length, stored bytes, and content SHA-256 before constructing either format. Regular and symlink entries must resolve to a verified Git blob; a submodule entry is verified only as a 20-byte gitlink object ID from the tree and is never passed to `cat-file blob`, fetched, or cloned. Git OIDs are recorded as Git object identities and are never substituted for SHA-256 content digests. The exact resource limits are checked before allocation and again after decoding; truncated, reordered, trailing, duplicate, alias, and oversized fixtures each have the stated deterministic code/path.

The report binds `candidate.commit_oid`, `candidate.root_tree_oid`, every `source.manifest.entries[i].object_oid` or gitlink identity, `candidate.source_manifest_sha256`, `candidate.source_bundle_sha256`, `candidate.source_manifest_preimage_sha256`, and `candidate.source_bundle_preimage_sha256`. It also binds `base.program_blob_oid`, `candidate.program_blob_oid`, `base.program_bytes_sha256`, and `candidate.program_bytes_sha256`, where each PROGRAM digest is recomputed over the exact Git-extracted raw bytes. Missing, changed, omitted, added, reordered, duplicated, mode/type-mutated, truncated, trailing, mismatched, or digest-aliased bytes produce PI_SOURCE_BINDING at `source.bundle` in phase `source_bundle` with exit status 14; the detail and evidence carry the first exact entry or binding location.

`SourceManifest/v2` `total_size` is exactly `source_total_size = sum(entry.length for every manifest entry in manifest order)`, including the 20-byte content length of each submodule record, and it is equal to the sum of SourceBundle content-length fields. The adapter recomputes `source_total_size` with checked integer arithmetic before allocation and rejects any mismatch before source analysis; `source_total_size` is at most 8,388,608 bytes, so the same bound applies to both the manifest content total and the bundle content total independently of framing overhead, while each regular-file length is independently at most 8,388,608 bytes.

First, a candidate shorter than the base, or any candidate whose raw-row multiset lacks any base row with its full multiplicity, is PI_HISTORY_DELETE. Second, a same-length candidate with the same raw-row multiset but any row at a different index is PI_HISTORY_REORDER. Third, an exact base prefix permits only complete new rows after that prefix, and an appended duplicate is checked after the prefix test. Every remaining non-prefix mutation is PI_HISTORY_REWRITE. An insert in the middle, reorder-then-append, or append-then-rotate is PI_HISTORY_REWRITE. A pure same-length permutation is PI_HISTORY_REORDER. An appended exact raw duplicate is PI_HISTORY_DUPLICATE. These classifications are deterministic and total.

History errors report exact section, first differing zero-based index, one-based source line when available, base and candidate row counts, raw row digests, retained-prefix digest, and multiplicity evidence without echoing raw secrets. Sections 18 and 19 always use the actual immutable event base commit, never a branch name, a contributor-provided base file, or a symbolic merge ref. Policy-removal and authority-update records are valid only when their exact decision-log row bytes are appended after the retained base prefix.

The history result is total and uses this precedence independently for Sections 18 and 19: (1) if candidate row count is less than base count or any base raw-row digest multiplicity is absent, emit PI_HISTORY_DELETE; (2) otherwise find the first differing index; if no index differs, accept an exact prefix unless the suffix contains a retained raw-row duplicate, which emits PI_HISTORY_DUPLICATE; (3) if candidate and base raw-row multisets are equal, emit PI_HISTORY_REORDER; (4) if every base row is an exact prefix and all suffix rows are complete new physical rows, accept append; (5) every other candidate emits PI_HISTORY_REWRITE. This order classifies delete-plus-append as DELETE, reorder-then-append and append-then-rotate as REWRITE, pure permutation as REORDER, and append of an exact retained row as DUPLICATE. Section selection, row identity, indexes, line rendering, and raw-byte digests are those in Section 9; there is no stale-vs-invalid history branch.

## 10. Immutable Git-object trust and branch ancestry

All Git object access happens outside the isolated container in a trusted host adapter. The adapter obtains immutable event-bound commit SHAs, verifies exact 40-lowercase-hex syntax, verifies canonical repository ownership, resolves commit objects, and computes merge ancestry from those SHAs. It uses canonical GitHub pull-request refs `refs/pull/N/head` and `refs/pull/N/merge` only; N is the validated pull-request number, and it never fetches a contributor-fork URL, clone URL, arbitrary ref, or event-supplied remote.

For every base, candidate, merge, workflow, and source object, the adapter records and verifies commit OID, root tree OID, required blob OIDs, Git object type, byte length, and content SHA-256. It verifies each recorded tree equals its commit’s immutable root tree. It resolves each root-tree entry with `git ls-tree --full-tree -z`, verifies it with `git cat-file -t` and `git cat-file -s`, and extracts bytes only with `git cat-file blob <verified blob oid>`; it never reads PROGRAM.md through a candidate filesystem path. Base and candidate PROGRAM.md are root-tree entries whose exact path bytes are `PROGRAM.md`, exact type `blob`, and exact mode `100644`. A missing candidate entry is PI_PROGRAM_MISSING at `candidate.tree.PROGRAM.md` in phase `candidate_tree` with exit status 14. A symlink, submodule, traversal entry, unexpected slash, duplicate tree entry, wrong mode, or non-blob entry is PI_CANDIDATE_TREE_ENTRY at the exact entry path in phase `candidate_tree` with exit status 14.

The adapter extracts verified base and candidate PROGRAM blob bytes into fresh immutable input files named by logical role, not candidate paths. It extracts the complete tracked tree into SourceManifest/v2 and SourceBundle/v2, and passes verified governance bytes. The container receives read-only mounts for those bytes, trusted validator source, and trusted tests only. It never receives a candidate checkout and never opens a candidate filesystem path named PROGRAM.md. The report binds every mounted byte to its commit/tree/blob OID and content digest.

The exact immutable validator roles are `base_program_bytes`, `candidate_program_bytes`, `base_commit_oid`, `base_tree_oid`, `base_program_blob_oid`, `candidate_commit_oid`, `candidate_tree_oid`, `candidate_program_blob_oid`, `merge_base_oid`, `candidate_source_manifest`, `candidate_source_bundle`, `event_json`, `governance_evidence`, and `report_json`. Symbolic base, head, candidate-root, candidate-program, or branch arguments do not exist. Every SHA role is a verified immutable object identity; every byte role has a recomputed SHA-256 preimage digest.

For a pull request, the typed event binding is canonical repository `omarchy-silicon/omarchy-apple-platform`, PR number N, event base `B = pull_request.base.sha`, canonical PR head `H = refs/pull/N/head`, merge candidate `C = refs/pull/N/merge`, and trusted base ref `refs/heads/main`. The trusted base ref must resolve to exactly B at verification time. The candidate commit must have exactly two parents in order `[B,H]`. The branch-up-to-date predicate is exact and mandatory: `git merge-base H B` must equal B, which proves B is an ancestor of H and therefore the PR head contains the required event base. Candidate-parent shape alone is insufficient. Failure of either the ancestry predicate or the required strict-update boolean is PI_BRANCH_NOT_UP_TO_DATE at `trust.branch_up_to_date` in phase `trust` with exit status 14; an event/trusted-ref mismatch is PI_BRANCH_BASE_MOVED, and a candidate-parent/ref mismatch is PI_MERGE_CANDIDATE_STALE.

For a merge queue event, the binding is canonical repository, `merge_group.base_sha=B`, `merge_group.head_sha=H`, and `github.sha=C` as queue candidate. The adapter verifies candidate parent order, B is an ancestor of H when the queue contract requires the PR head, and H is an ancestor of C. It records queue identity and base/head/candidate state; missing or inconsistent queue state is PI_MERGE_QUEUE_STATE at `merge_queue.state` in phase `workflow_trust`. For a push event, the binding is canonical repository, `after` or `github.sha=C`, and the first parent B; `before` must equal B for post-merge main verification. Any missing or inconsistent event kind or field set is PI_EVENT_UNSUPPORTED at `event.schema` in phase `workflow_trust` with exit status 14. PI_EVENT_UNSUPPORTED never reports a Git/ref or endpoint fault.

The adapter recomputes all ref and ancestry evidence after each mutable GitHub/API read and immediately before report finalization. It re-resolves trusted base, canonical PR head, merge candidate, commit parents, root trees, and required check head SHA; any movement or disagreement invalidates the current evidence as PI_REF_MOVED at `trust.refs` in phase `trust` with exit status 14. It must then start a fresh event-bound run with the new immutable SHAs; a prior report, old candidate, or local branch cannot be reused. A merge queue candidate that moves or is regenerated is stale until all bindings and the ancestry predicate are recomputed.

Branch protection evidence must show strict required-status-check updates enabled for the protected `main` ref. The required-update rule is a boolean `strict=true` bound to the exact branch-protection rule ID, settings version, API response digest, and freshness record. Missing protection is PI_BRANCH_PROTECTION_MISSING; strict=false is PI_BRANCH_NOT_UP_TO_DATE; stale settings are PI_BRANCH_PROTECTION_STALE. A post-merge failure on main quarantines promotion, routes an owner incident, and requires a fresh successful verification at the new main SHA; rerun, warning text, or a stale report cannot remediate it.

## 11. GitHubGovernanceEvidence/v1 adapter input

The host adapter emits one typed `GitHubGovernanceEvidence/v1` value plus the exact event JSON bytes/digest pair. The canonicalization contract is RFC 8785 JSON Canonicalization Scheme (JCS), using RFC 8259 strict parsing, UTF-8 output, ECMAScript-compatible shortest number serialization, UTF-16 code-unit property ordering required by RFC 8785, no whitespace, no duplicate names, and no NaN or Infinity. `ensure_ascii`, UTF-8-byte key sorting, Python `repr`, and a custom escaping profile are forbidden. The required implementation identity is `RFC8785:2019; parser=CPython-3.13.5-json-strict; canonicalizer=rfc8785==0.1.4; image=python:3.13.5-slim-bookworm@sha256:a7cb177dc60dfa77b223192cd0d9e6ce1aac7cf9a569023d68e7c91b6371a718; platform=linux/amd64`; the package source or wheel digest and toolchain identity must be recorded before execution. The canonicalizer and validator are NOT IMPLEMENTED at this design tip; the pinned contract remains exact and a future implementation may not substitute host Python or a different library. Unknown keys, missing required keys, duplicate identities, contradictory duplicate responses, noncanonical reserialization, or non-UTF-8 bytes fail closed. The top-level keys in the JCS-sorted order are `api_responses`, `app_authority`, `branch_protection`, `check_runs`, `codeowners`, `event`, `merge_queue`, `replay_store`, `required_contexts`, `reviews`, `schema`, and `workflow`.

The exact evidence schema is:

The event JSON file is hashed over exact bytes and must have an allowlisted kind of `pull_request`, `merge_group`, or `push`, canonical repository exactly `omarchy-silicon/omarchy-apple-platform`, and only the fields needed for that event contract. The typed event fields must equal the corresponding event JSON fields after strict parsing, and the event JSON digest and length must be recomputed. Invalid UTF-8, duplicate names, invalid escapes, noncanonical JCS bytes, malformed JSON, non-integer schema values, or digest/length mismatch is PI_EVENT_JSON at `event_json` in phase `workflow_trust` with exit status 14. An otherwise valid JSON value with an unsupported kind or a field set not exactly allowed for that kind is PI_EVENT_UNSUPPORTED at `event.schema` in phase `workflow_trust` with exit status 14; PI_EVENT_UNSUPPORTED never appears in phase `trust` and never covers an arbitrary endpoint or repository.

The trusted workflow must be exact path `.github/workflows/program-integrity.yml`, source ref `refs/heads/main`, mode `100644`, regular blob type, and immutable commit/tree/blob/content identities bound to the protected base. A wrong path is PI_WORKFLOW_PATH at `workflow.path` in phase `workflow_trust` with exit status 14; a missing or malformed trusted object, candidate-controlled source, changed workflow source, wrong mode, or untrusted source is PI_WORKFLOW_SOURCE_UNTRUSTED at `workflow.source`; the trusted CODEOWNERS object must be exact path `.github/CODEOWNERS`, mode `100644`, regular blob, and its rule match must resolve both workflow and CODEOWNERS changes to `@omarchy-silicon/platform-ci-owners`, otherwise PI_CODEOWNERS_UNTRUSTED at `codeowners.matched_rule`; all three are in phase `workflow_trust` with exit status 14.

At least one current non-dismissed `APPROVED` review by the exact matched owner identity is required for workflow or CODEOWNERS changes. The approval must target the current PR head SHA, be submitted after that head was created, and be younger than the evidence freshness limit. No qualifying review, `CHANGES_REQUESTED`, `DISMISSED`, anonymous, or unresolvable identity is PI_OWNER_REVIEW_MISSING at `reviews[0]` for the first review fixture, or the actual indexed renderer otherwise, in phase `workflow_trust` with exit status 14. An otherwise qualifying approval for an earlier head or beyond the freshness limit is PI_OWNER_REVIEW_STALE at the same exact indexed path. A workflow-only PR without this review is PI_WORKFLOW_REVIEW_REQUIRED at `.github/workflows/program-integrity.yml` in phase `workflow_trust` with exit status 14. Review order is ascending `(submitted_at, identity, response_sha256)` and the primary missing/stale index is the smallest failing index.

Branch protection must have a non-empty exact `rule_id`, protected ref `refs/heads/main`, current settings version, `strict=true`, `enforce_admins=true`, `require_code_owner_reviews=true`, required review count at least one, and merge queue requirement true for queue events. `required_contexts` must contain exactly one sorted entry: `program-integrity-ci / program-integrity__9a6d4c2e8f17b0a3`, its provider must be the trusted GitHub Actions app, and its workflow blob OID must equal the trusted workflow. A missing or renamed context is PI_REQUIRED_CONTEXT_MISSING at `required_contexts`; absent/no-protection is PI_BRANCH_PROTECTION_MISSING at `branch_protection.rule_id`; a valid but old settings response is PI_BRANCH_PROTECTION_STALE at `branch_protection.response_sha256`; and contradictory API values are PI_API_AMBIGUOUS at `api_responses[0]` for the first response fixture, or the actual indexed renderer otherwise, all in phase `workflow_trust` with exit status 14. `strict=false` is evaluated as the same `PI_BRANCH_NOT_UP_TO_DATE` predicate and rendered at `trust.branch_up_to_date`; no branch-protection fault uses a second path for that code. Required-context order is ascending `(context, provider, workflow_path, workflow_blob_oid)`.

Every check run identity is the tuple `(id, name, app_id, provider, workflow_path, workflow_blob_oid, head_sha)`. IDs are unique, names are exact, providers are allowlisted, workflow source is trusted, head SHA equals the current event candidate/head as appropriate, status is `completed`, and conclusion is `success`. A duplicate display name, short-name collision, PR-side duplicate job, or untrusted app is PI_CHECK_IDENTITY at `check_runs[0]` for the first check fixture, or the actual indexed renderer otherwise, in phase `workflow_trust` with exit status 14. A stale head, non-completed status, non-success conclusion, or contradictory result is PI_CHECK_STALE at that exact indexed path. Check-run order is ascending `(id, name, provider, head_sha)` and no check run can satisfy protection by name alone.

Every API response listed in `api_responses` is content-digested, timestamped, and within its declared maximum age of 300 seconds. Required endpoints are a closed set of branch protection, required contexts, check runs, reviews, workflow blob, CODEOWNERS blob, app installation, and merge-queue state, and each occurs exactly once. A missing, duplicate, contradictory, or ambiguous response is PI_API_AMBIGUOUS at `api_responses[0]` for the first response fixture, or the actual indexed renderer otherwise, in phase `workflow_trust` with exit status 14. API-response order is the closed endpoint order above, then ascending endpoint bytes for any explicitly repeated subresource; duplicates are rejected before sorting. `app_authority` must identify a verified installation with authority over the canonical repository and the named owner team, with no write permission beyond the declared CI/check/artifact operations; missing or mismatched installation authority is PI_APP_UNAUTHORIZED at `app_authority` in phase `workflow_trust` with exit status 14.

The required evidence codes are exact: PI_EVENT_JSON, PI_EVENT_UNSUPPORTED, PI_REPOSITORY_UNTRUSTED, PI_WORKFLOW_SOURCE_UNTRUSTED, PI_WORKFLOW_PATH, PI_CODEOWNERS_UNTRUSTED, PI_OWNER_REVIEW_MISSING, PI_OWNER_REVIEW_STALE, PI_WORKFLOW_REVIEW_REQUIRED, PI_BRANCH_PROTECTION_MISSING, PI_BRANCH_PROTECTION_STALE, PI_REQUIRED_CONTEXT_MISSING, PI_CHECK_IDENTITY, PI_CHECK_STALE, PI_MERGE_QUEUE_STATE, PI_API_AMBIGUOUS, PI_APP_UNAUTHORIZED, PI_REF_MOVED, PI_BRANCH_BASE_MOVED, PI_BRANCH_NOT_UP_TO_DATE, and PI_MERGE_CANDIDATE_STALE. Each has one exact path, one predicate, phase `workflow_trust` or `trust` as specified above, nonzero exit status 14, and a detail containing only digests, identities, timestamps, and expected/actual enum values. `PI_EVENT_JSON` is only parser/canonical-byte failure at `event_json`; `PI_EVENT_UNSUPPORTED` is only allowlist/schema failure at `event.schema`, so the prior phase collision is impossible.

The closed `api_responses` array order is exactly `branch_protection`, `required_contexts`, `check_runs`, `reviews`, `workflow`, `codeowners`, `app_authority`, `merge_queue`; each endpoint’s response digest is computed over its exact response bytes before the array is canonicalized. JCS parsing also rejects lone UTF-16 surrogate escapes and non-scalar Unicode values before canonicalization; this is covered by the JCS-SURROGATE project vector alongside the invalid-UTF-8 vector.

All report and evidence JSON uses the RFC 8785 JCS contract in Section 11: UTF-8, no BOM, no whitespace outside tokens, RFC 8259 string escapes, ECMAScript shortest numbers, UTF-16 code-unit key order, no duplicate names, and no NaN or Infinity. The final report has exactly one LF after its JCS bytes. A failure record is exactly {code, phase, path, detail, line, row_index, evidence}, where line is a one-based integer or null, row_index is a zero-based integer or null, and evidence is an ordered array of {name, value, sha256} records. A phase record is exactly {name, state, blocked_by, failures}. The fail census is an ordered array of failure records, not a count-only summary. Credentials, raw environment, source bytes, reason bytes, and signatures are redacted; their exact lengths and digests remain bound.

The canonical path renderer is byte-stable: path = segment followed by zero or more dot-segments or bracket indexes, segment = ASCII letter or underscore followed by ASCII letters, digits, or underscore, index = 0 or a nonzero digit followed by digits, and quoted IDs or ItemIDs use the exact closed ASCII grammars defined below with no escaping. A validated unique ID may use ledger.rows["ID"].depends; before an ID is known or when duplicates exist, the indexed renderer is mandatory. The exact renderers are ledger.rows[i], ledger.rows[i].field, authority.section12_1, policy.diff.removed["ITEM_ID"], policy.f07.direct_edges["ID"], history, history.section18.rows[i], history.section19.rows[i], source.manifest.entries[i], source.bundle.entries[i], workflow.source, reviews[i], check_runs[i], and report.binding, with i replaced by its shortest decimal. No line-token placeholder or implementation-defined path is permitted.

The canonical report preimage is the JCS UTF-8 byte sequence of the complete report object with its top-level `report_sha256` member omitted, with no trailing LF. `report_sha256` equals SHA-256 of that preimage; the final artifact is the JCS UTF-8 byte sequence of the complete object after inserting that digest at its JCS-sorted member position, followed by exactly one LF. A digest field is never included in its own preimage, and the final digest member is not forced to the end of the object. PASS requires result=PASS, exit_status=0, the `SuccessPrimary` PI_OK value, every phase PASS, zero failure records, zero blocked records, complete authority/source/governance/invocation evidence, exact current bindings, and no unavailable tool. FAIL requires result=FAIL, a primary code, exact phase/path/detail, all executed failure records, and explicit BLOCKED phase records. Warning is not a result or state. A nonempty fail census, warning-like text, missing evidence, stale binding, nonzero child status, or unavailable tool cannot coexist with PASS.

Human output is one deterministic line per failure in the form `FAIL code phase path detail` followed by one `BLOCKED phase blocked_by` line for each gated phase, using the same failure and phase order as JSON. It never labels a required failure as a warning and never prints PASS after a failure. A failed earlier phase controls all dependent phase states but independent history evidence may still be reported.
