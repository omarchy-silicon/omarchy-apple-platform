## 1. Purpose, authorities, and boundaries

The future system validates the coordinator-owned PROGRAM.md as a plan-integrity input. It parses the canonical five-column slice ledger, computes its dependency graph, checks the status census, proves dynamic F-07 closure and coordinator-declared direct prerequisites, audits the sole stable-promotion seam, and verifies that decision and progress history is append-only against the immutable event base. It emits deterministic JSON, a human fail census, and phase-gating evidence.

Plan integrity is not release readiness. A passing plan-integrity result does not establish implementation, signing, reproducibility, legal distribution, board qualification, physical evidence, installer safety, hardware compatibility, support, release, or DONE. F-07 remains the sole stable-promotion authority, and this design never authorizes a release or changes branch protection.

The human-produced opaque boundary named by PROGRAM.md is outside this design. The future validator receives only externally declared boundary metadata and never reads, traverses, characterizes, builds, or tests any source under that boundary. The one existing opaque external dependency literal remains an exact byte token only; it is never resolved to a path, repository, source, or executable.

The consumed authorities are the pinned-parent AGENTS.md, the pinned-parent PROGRAM.md, and typed canonical GitHub event, governance, and Git-object metadata. AGENTS.md supplies one-writer, coordinator-only DONE, append-only history, reviewer, and fail-closed rules; it does not supply an exact-base rule. The task assignment and event contract supply the immutable base and parent requirements. PROGRAM.md supplies the ledger, its acceptance section, its policy declaration when added, its status vocabulary, and Sections 18 and 19. The coordinator base is the only acceptance authority unless an owner-ratified FoundationAuthorityUpdate/v1 record is validly supplied.

## 3. Raw-byte and Markdown contract

The validator consumes raw bytes without Markdown rendering, HTML conversion, Unicode normalization, whitespace normalization, line-ending conversion, or reserialization. Every physical line ends in exactly one ASCII LF byte except that the final line may omit LF. Any CR byte, including CRLF, is PI_LINE_ENDING at `PROGRAM.md` in phase `preflight` with exit status 10. UTF-8 is decoded only after the raw line-ending check.

The rejected control set is U+0000 through U+0009, U+000B through U+000C, U+000E through U+001F, and U+007F through U+009F. LF U+000A is the only permitted control character. Tabs, DEL, C1 controls, and CR are therefore never accepted. PI_CONTROL_CHAR reports the byte offset, code point, source path, and phase `preflight`; PI_LINE_ENDING takes precedence for CR. A NUL, invalid UTF-8 sequence, or C1 byte is never interpreted as a delimiter or line boundary.

All structural delimiters are ASCII bytes: `|` U+007C, `-` U+002D, `,` U+002C, and ASCII space U+0020. Fullwidth, confusable, non-ASCII, or normalized delimiter characters are not delimiters. Cell-edge trimming removes ASCII spaces only; it does not remove tabs, non-breaking spaces, or any other character. Every accepted ASCII token is compared byte-for-byte and case-sensitively.

The scanner is a total byte state machine with states `NORMAL`, `FENCE`, `COMMENT`, and `CODE_SPAN`. A fence opener is a physical line whose first byte is ASCII space repeated zero through three times, followed by at least three identical backticks or tildes; its trailing bytes are an opaque info string and the line must have its normal LF termination. A closer uses the same fence character, has at least the opener length, and may have only ASCII spaces after the run before LF. A shorter run or non-space trailing byte is content, not a closer. Fence openers are not nested: an opener-looking line inside `FENCE` is literal content and a target-shaped line there is recorded as a laundering lookalike. EOF in `FENCE` is PI_FENCE_UNTERMINATED at `PROGRAM.md.fence` in phase `preflight` with exit status 10.

An HTML comment starts at the exact byte sequence `<!--` outside `FENCE` and ends at the exact byte sequence `-->` outside `FENCE`; comment state is byte-stream based and may cross physical lines. A second `<!--` in `COMMENT` is PI_COMMENT_NESTED, a `-->` in `NORMAL` is PI_COMMENT_CLOSE, and EOF in `COMMENT` is PI_COMMENT_UNTERMINATED. Each is at `PROGRAM.md.comment` in phase `preflight` with exit status 10. Target-shaped headings, headers, delimiters, and rows inside a comment are recorded as lookalikes and cannot satisfy selection. A fence marker inside a comment is comment content, and a comment marker inside a fence is fence content.

An inline code span outside `FENCE` and `COMMENT` starts with a run of one or more backticks and closes only on the same physical line with a run of exactly the same length. Its content is literal and cannot create a structural heading, table, or comment; if it contains target-shaped material, the scanner records PI_MARKDOWN_LAUNDERED at `PROGRAM.md.literal` in phase `preflight` with exit status 10. An unmatched span is PI_CODE_SPAN_UNTERMINATED at the same path and phase. Leading indentation of one through three spaces makes a target-shaped line nonstructural and records a lookalike; four or more spaces is code content and records a lookalike. Tabs are rejected before indentation classification. A structural heading or table line must begin at byte column zero and have no trailing spaces.

The parser selects exactly one structural raw line `## 12. Slice ledger` and exactly one structural raw line `### 12.1 Foundation slice acceptance`, with those exact bytes and no trailing spaces. The Section 12 region starts at the `#` byte of the selected `## 12. Slice ledger` line and ends immediately before the next exact structural `## ` heading, or at EOF. Every raw byte in that region is scanned for duplicate or laundered target material. A duplicate structural heading, duplicate table candidate, or lookalike paired with a missing real target is PI_LEDGER_TABLE at `PROGRAM.md` in phase `ledger_parse` with exit status 10.

The Section 12.1 acceptance region starts at its exact structural heading and contains exactly one contiguous acceptance table with the exact three-column header `| Slice | Required executable artifacts | Hard rejection conditions |`, one delimiter row with three cells containing exactly `---`, and the six foundation rows F-02 through F-07 from the coordinator base authority. Its table ends at the first blank LF line after the contiguous table. Text between that table and the ledger is prose and must not contain another ledger header or table candidate, whether rendered, fenced, commented, code-spanned, or HTML-shaped. A missing, duplicate, or laundered acceptance table is PI_ACCEPTANCE_AUTHORITY at `authority.section12_1` in phase `authority` with exit status 14.

The ledger is the only table in the Section 12 region with the exact structural header `| ID | Repository | Deliverable | Depends on | Status |`. The selected ledger begins at that exact header, includes its exact delimiter row and at least one data row, and ends at the first blank LF line or exact structural heading after the contiguous data rows; every intervening pipe-prefixed line is part of the table and must parse. There must be exactly one such header, exactly one five-column ledger table, and no duplicate exact heading, duplicate table, table-shaped lookalike, or alternate rendering of it anywhere in the raw Section 12 region. An HTML table, rendered HTML, Markdown AST, code-fence table, HTML-comment table, or second table cannot satisfy selection; a fake target in any of those forms is evidence of laundering and fails PI_LEDGER_TABLE.

A five-column ledger row has exactly six ASCII `|` delimiters: a leading delimiter, four internal delimiters, and a trailing delimiter, yielding five cells. “Six delimiters” is the precise boundary rule; five delimiters is malformed. The header, delimiter row, and every data row use this same six-delimiter rule. A cell cannot contain a pipe, including a backslash-escaped pipe or a pipe inside a code span; multiline cells are forbidden because each row is exactly one physical source line.

The ledger header cells must be exactly `ID`, `Repository`, `Deliverable`, `Depends on`, and `Status` after ASCII-space edge trimming. The delimiter row must contain exactly five cells, each exactly `---` after ASCII-space edge trimming. Any missing, duplicated, or lookalike header, delimiter, or data table is PI_LEDGER_TABLE at `PROGRAM.md` in phase `ledger_parse` with exit status 10. A pipe-prefixed malformed line within the selected table is PI_ROW_SHAPE, not ignored prose.

Each data row has exactly five non-empty cells in the same order. The row record retains exact raw row bytes, exact source line, zero-based row index, byte start and end offsets, and parsed fields; every downstream phase consumes that record and never reparses the source. The source line number is one-based and counts physical LF-terminated lines from the first byte; the final unterminated line still has one line number. A ledger data row index is zero-based from the first data row after the delimiter row.

The ID grammar is ASCII and case-sensitive: `(B|F|G|I|K|P|Q)-[0-9]{2}`. The set of IDs is derived from the rows and never hard-coded. Status is exactly one of `DONE`, `IN PROGRESS`, `REVIEW`, `TODO`, or `HUMAN-ONLY BLOCKED`; an unknown status is PI_STATUS_UNKNOWN at the concrete rendered path `ledger.rows[0].status` when the first row is mutated, or the same renderer with the actual zero-based index in a generated fixture, in phase `ledger_parse` with exit status 10. A malformed ID prefix, width, separator, Unicode lookalike, or normalization is PI_ID_SYNTAX at `ledger.rows[0].id` for that same first-row fixture and the actual indexed renderer otherwise, in phase `ledger_parse` with exit status 10.

The dependency cell is either the exact ASCII token `none` or a non-empty sequence separated only by the exact two-byte delimiter `, `. No leading or trailing comma, extra space, missing space, empty token, tab, or other separator is accepted. A dependency token matching the ASCII ID-shaped grammar `[A-Z]-[0-9]{2}` is admitted to graph checking and becomes PI_DEP_UNKNOWN if that exact token is absent from the parsed row-ID set; this makes `Z-99` a graph unknown rather than a parser error. A token that does not match that ASCII shape is PI_DEP_SYNTAX at `ledger.rows[0].depends` for the first-row fixture and the actual indexed renderer otherwise, in phase `ledger_parse` with exit status 10. The one existing opaque external literal remains accepted only as an exact ASCII token and is never resolved. An empty dependency cell after ASCII-space edge trimming is PI_ROW_SHAPE; a leading, trailing, or doubled comma that creates an empty token is PI_DEP_EMPTY; doubled spaces, tabs, or another separator are PI_DEP_SYNTAX; and `none` combined with any other token is PI_DEP_SYNTAX. All three parser classifications use the stated path, phase, and exit status.

The graph phase, not the parser phase, reports repeated dependency tokens as PI_DEP_DUPLICATE at `ledger.rows[0].depends` for the first-row fixture and the actual indexed renderer otherwise, in phase `graph` with exit status 11. This fixes the duplicate-token phase boundary: lexical separator faults are parser failures, while exact repeated tokens are graph failures. Unknown graph IDs are PI_DEP_UNKNOWN, self-edges are PI_DEP_SELF, and cycles are PI_DEP_CYCLE, each at the exact rendered row/field or `graph.cycle` path in phase `graph` with exit status 11.

## 4. Coordinator-owned promotion policy and monotonic evolution

There is no promotion mode switch. Every invocation has the same promotion-policy precondition, and no invocation can return PI_OK until the required PROGRAM policy declaration exists and parses exactly. Until the declaration exists and parses exactly in the candidate PROGRAM, the policy phase is PI_POLICY_UNDECLARED at `policy.program_integrity` in phase `policy` with exit status 12, regardless of whether the invocation is local, pull-request, merge-queue, direct-push, or post-merge; an earlier trust or input failure may still control the overall primary result.

The minimum coordinator-owned declaration is an append-only policy history under Section 12 with this exact structural heading and exact record grammar. The code block specifies source bytes; its backticks are not part of PROGRAM.md.

```text
### 12.2 Program-integrity policy history

Program-integrity policy version: 1
Policy document ID: sha256:<64 lowercase hex>
F-07 mandatory direct prerequisites: F-05, P-03, P-05, I-09, B-04
Q cohort rows: ID matches Q-[0-9]{2} and Deliverable begins with the exact case-sensitive verb Certify followed by one ASCII space.
Allowed statuses: DONE, IN PROGRESS, REVIEW, TODO, HUMAN-ONLY BLOCKED
F-07 closure rule: Every parsed ledger ID is reachable from F-07 by dependency edges.
Acceptance authority: Section 12.1 rows F-02 through F-07 are pinned to coordinator base bytes.
Rejection behavior: Any unmet required condition returns FAIL with a nonzero exit and no PASS artifact.
```

The raw declaration is one exact heading line with LF, one blank LF, and one or more exact eight-line records, with one blank LF between records; the final record ends immediately before the first exact structural `## ` heading. The heading occurs exactly once outside fences, comments, and code spans, and no target-shaped heading or record occurs elsewhere in Section 12. The version is a positive ASCII decimal without leading zeroes, versions are unique and strictly increasing, and the direct-prerequisite value is a non-empty exact ASCII ID list separated by `, ` with no duplicate IDs; each ID must exist in the same ledger. The Q, status, closure, acceptance, and rejection lines are exact, including capitalization, punctuation, and final periods. The `Policy document ID` is not self-referential: it is `sha256:` plus 64 lowercase hex characters over the exact UTF-8 bytes of the other seven record lines from the version line through the rejection line, including each LF and excluding the ID line. The policy-history byte digest is SHA-256 over the exact bytes from the heading through the final record LF, including blank separators.

Each policy record expands to a canonical semantic map with these stable item IDs and exact values: `F07.DIRECT.<ID>` for every direct prerequisite, `Q.COHORT.RULE` for the exact Q line, `Q.COHORT.<ID>` for every derived qualifying Q row, `LEDGER.STATUS.VOCABULARY` for the exact status line, `F07.CLOSURE.RULE` for the exact closure line, `AUTHORITY.SECTION12_1` for the exact acceptance line, and `REJECTION.FAIL_CLOSED` for the exact rejection line. The semantic map also records source record version, source byte range, item byte digest, and consumer set. A policy document ID is recomputed from its exact bytes and is never accepted merely because its syntax is valid.

The monotonic comparison is a deterministic superset/diff algorithm. Parse the complete base and candidate histories from immutable PROGRAM bytes; require the base history to be an exact raw-byte prefix ending at a complete record boundary, require unchanged history to retain every raw byte, and select the highest version as effective. Build `B` and `C` as maps from semantic item ID to exact canonical value bytes. Compute `removed = {id in B where id is absent from C or C[id] != B[id]}`, `added = {id in C where id is absent from B or C[id] != B[id]}`, and `retained = B - removed`. A candidate with `removed` empty and `added` empty may retain the same version; any candidate with additions or a new effective record must have a strictly higher version. Every retained value must be byte-identical. A changed value is treated as removal plus addition, never as an implicit strengthening.

Direct prerequisites and Q cohort membership are set-valued requirements, so `C` must contain every `F07.DIRECT.<ID>` and `Q.COHORT.<ID>` present in `B`; adding a direct prerequisite or qualifying Q row is a monotonic addition. The Q rule itself is an exact retained value, so changing the verb, case, whitespace, predicate, or interpretation is a removal. Status vocabulary, closure rule, acceptance condition, and rejection behavior are exact retained requirements; they cannot be removed, shortened, replaced, or made less strict by editing text, changing a version, changing a Deliverable verb, or relying on a candidate-derived count. There is no silent Deliverable-verb shrinkage.

If `removed` is non-empty, the candidate must supply exactly one owner-authorized `PolicyRemoval/v1` record for that comparison. Without it, the result is PI_POLICY_DOWNGRADE at `policy.diff.removed["F07.DIRECT.P-03"]` for the P-03 fixture, or the exact quoted-item renderer for the actual first removed item, in phase `policy` with exit status 12. An authorization record cannot hide an additional removed item, preserve a changed item under the old ID, or authorize a changed acceptance table; those cases remain failures. If a record is present when `removed` is empty, the result is PI_POLICY_REMOVAL_UNEXPECTED at `policy_removal` in phase `policy` with exit status 12.

`PolicyRemoval/v1` is an exact UTF-8 record with LF-terminated ASCII field names in this order and no other fields: `PolicyRemoval/v1`, `previous_policy_document_id=sha256:<64 lowercase hex>`, `previous_policy_sha256=sha256:<64 lowercase hex>`, `previous_version=<positive decimal>`, `new_policy_document_id=sha256:<64 lowercase hex>`, `new_policy_sha256=sha256:<64 lowercase hex>`, `new_version=<positive decimal>`, `removed_semantic_item_ids=<sorted comma-space list of exact item IDs>`, `reason_b64=<RFC4648 base64 with padding>`, `signer=<canonical owner identity>`, `role=<coordinator|repository-owner>`, `context_b64=<RFC4648 base64 with padding>`, `timestamp=<UTC RFC3339 second precision ending Z>`, `expiry=<UTC RFC3339 second precision ending Z>`, `replay_identity=<lowercase UUID>`, `decision_log_row_b64=<RFC4648 base64 with padding>`, `decision_log_row_sha256=sha256:<64 lowercase hex>`, `affected_consumers=<sorted comma-space list of exact consumer IDs>`, and `signature_b64=<RFC4648 base64 with padding>`. The signature is Ed25519 over all preceding record bytes including their LF; its public key and signer-to-role binding come only from the trusted governance authority.

The removal validator recomputes both policy byte digests and document IDs, checks previous and new versions, requires `removed_semantic_item_ids` to equal the computed `removed` set exactly, decodes the reason/context and decision-log row, recomputes the row digest, and requires that exact raw row including its LF to be a newly appended Section 18 row in the candidate. It requires an allowed signer and role, `timestamp <= current trusted time < expiry`, expiry no more than 30 days after timestamp, a unique replay identity not previously accepted, and an affected-consumer set equal to the consumers of all removed items. Missing, malformed, unsigned, wrong-key, wrong-digest, wrong-version, wrong-row, expired, replayed, or extra-field records are PI_POLICY_REMOVAL_INVALID at `policy_removal` in phase `policy` with exit status 12; a validly shaped record with stale bytes or expired freshness is PI_POLICY_REMOVAL_STALE, and a reused identity is PI_POLICY_REMOVAL_REPLAY. The report records previous/new document IDs, versions, item IDs, record digest, decision-log row digest, signer, role, context digest, expiry, replay identity, and affected consumers without exposing secret or raw reason bytes.

The current pinned base has no policy history, so its policy byte sequence is empty and its honest policy result is PI_POLICY_UNDECLARED. The positive fixture must add version 1 with the exact current five policy direct prerequisites and the derived five Q cohorts, producing ten direct F-07 dependencies. The fixtures must include independent removal records for P-03, P-05, I-09, B-04, and each selective Q removal; every one must fail if its record is missing or binds the wrong prior/new bytes. A record authorizing one removed item must fail when two are removed, and a record authorizing a Q removal must fail if the Q rule or any direct prerequisite is also changed.

## 6. Graph, closure, and phase gating

After a complete ledger parse and authority check, graph checks run in this exact order: duplicate IDs, unknown graph dependencies, repeated dependency tokens, self-edges, and cycles. A graph error prevents topological traversal, status census, F-07 closure, and F-07 direct-edge evaluation from claiming success. Kahn traversal represents `A depends on B` as edge B to A and uses a min-heap ordered by canonical ASCII ID, so dependencies precede consumers deterministically. A cycle witness follows lexicographically sorted outgoing dependency edges from the smallest unvisited node and rotates the closed witness to its smallest first ID.

F-07 policy checks require exactly one F-07 row. The closure is the recursively reachable graph-dependency set from F-07 and must equal the complete parsed ID set. A missing ID is PI_F07_CLOSURE at `policy.f07.closure["P-08"]` for the P-08 fixture, or the exact quoted-ID renderer for the actual missing ID, in phase `promotion` with exit status 12. The closure check is dynamic and automatically includes a newly added ledger ID when that ID is connected to F-07.

The direct-edge set is the union of exact IDs parsed from the effective policy record and the non-empty derived Q cohort set. Each required edge must occur literally in F-07’s dependency token sequence. A transitive path, an independently observed artifact, or an evidence claim never substitutes for a direct declaration. Each missing edge is PI_F07_DIRECT_EDGE at `policy.f07.direct_edges["P-08"]` for the P-08 fixture, or the exact quoted-ID renderer for the actual missing ID, in phase `promotion` with exit status 12; the fail census includes all missing edges and the lexicographically first missing edge controls the primary detail.

Each phase has exactly one state: PASS, FAIL, or BLOCKED. Trust, authority, and preflight failures block every dependent phase. A ledger-parse failure blocks graph, status, closure, and promotion phases, so a simultaneous table and graph mutation reports PI_LEDGER_TABLE as primary and records graph as BLOCKED rather than claiming a semantic graph error. Policy presence and exact grammar are checked after preflight and before promotion; history is independent of graph semantics and may run after trust and preflight. The report records every phase state and its `blocked_by` code; SKIPPED is not a possible unreported state.

The status census is computed only after complete lexical and graph validation. It contains total, counts for all five allowed statuses including zero, and sorted ID lists for each status. It never infers state from prose, branch names, commit messages, or Sections 18 and 19.

The pinned-base ground truth is a recomputed baseline, not a structural policy constant: 52 ledger rows, 52 unique IDs, zero missing internal dependencies, zero cycles, a deterministic 52-node traversal, F-07 closure 52/52, status census 1 DONE / 1 IN PROGRESS / 0 REVIEW / 44 TODO / 6 HUMAN-ONLY BLOCKED, five current Q cohorts, ten current direct F-07 dependencies, one future stable-promotion writer model, and 30 future paths absent. The implementation and tests must derive and print these values from pinned bytes and policy; they must not use a hard-coded 52, current Q list, or current path count as authority.

## 7. Canonical SourceManifest/v1 and SourceBundle/v1

The trusted host adapter produces SourceManifest/v1 and SourceBundle/v1 from the immutable candidate commit and root tree. These are canonical byte formats, not descriptive labels. The manifest is UTF-8 bytes whose ASCII grammar is exact, has no BOM, uses one LF after every line, and has no final digest line omitted. Header and field names are ASCII and case-sensitive. In the grammar block, each displayed `\t` denotes one ASCII HTAB byte U+0009, not two backslash characters; a literal backslash followed by `t` is invalid. A manifest is exactly:

```text
SourceManifest/v1
commit_oid=<40 lowercase hex>
root_tree_oid=<40 lowercase hex>
entry_count=<positive ASCII decimal or 0>
total_size=<ASCII decimal>
E\t<base64url-no-pad path bytes>\t100644\tregular\t<ASCII decimal length>\tsha256:<64 lowercase hex>\t<40 lowercase hex blob oid>
manifest_sha256=sha256:<64 lowercase hex>
```

The `manifest_sha256` value is the SHA-256 of the exact manifest preimage from byte zero through the LF ending the last `E` line, excluding the digest line itself. The entry count and total size are recomputed; no duplicate header, unknown key, blank line, extra field, missing field, or alternate encoding is accepted. A zero-entry manifest is valid as a source object but cannot satisfy the stable-writer seam, which reports PI_STABLE_WRITER_SEAM_ABSENT.

The path token decodes with RFC 4648 base64url without padding to raw path bytes. Those bytes must be valid UTF-8 and ASCII only, contain no NUL, backslash, colon, control, non-breaking space, or non-ASCII byte, be relative, have no leading slash, trailing slash, empty component, `.` component, or `..` component, and match `src/release/` followed by at least one component. Canonical order is ascending raw path-byte lexicographic order; paths are unique. Every entry has exact mode `100644`, exact type `regular`, exact decimal length, exact content SHA-256 over its bytes, and exact Git blob OID. Symlinks, submodules, directories, executable modes, other file types, traversal, absolute paths, NULs, aliases, and duplicate entries are rejected as PI_SOURCE_ENTRY at `source.manifest.entries[0]` for the first-entry fixture and the actual indexed renderer otherwise, in phase `source_bundle` with exit status 14.

SourceBundle/v1 is a binary preimage with no text decoding. Bytes 0 through 15 are exactly the 16-byte ASCII sequence `SOURCE-BUNDLE/1` followed by one NUL byte. Bytes 16 through 19 are an unsigned big-endian u32 entry count. For each manifest entry in manifest order, the bundle contains an unsigned big-endian u32 path-byte length, the exact decoded path bytes, an unsigned big-endian u32 mode value `0100644`, one byte type value `0x01` for regular file, an unsigned big-endian u64 content length, exactly that many content bytes, and 32 raw digest bytes equal to the entry’s content SHA-256. There is no padding, terminator, footer, alternate integer width, or digest alias. The bundle digest is SHA-256 over every bundle byte from offset zero through EOF, and its size is bounded by the source-bundle limit.

The manifest-to-bundle relation is exact: counts, order, decoded path bytes, mode, type, length, content digest, and content bytes must agree one-for-one; the bundle has no omitted, added, reordered, truncated, or trailing record. For each entry the adapter independently verifies Git commit OID, root-tree OID, path bytes, mode, type, blob OID, blob byte length, blob bytes, and content SHA-256 before constructing either format. Git OIDs are recorded as Git object identities and are never substituted for SHA-256 content digests.

The report binds `candidate.commit_oid`, `candidate.root_tree_oid`, every `source.manifest.entries[0].blob_oid` for the first-entry fixture and the actual indexed renderer otherwise, `candidate.source_manifest_sha256`, `candidate.source_bundle_sha256`, `candidate.source_manifest_preimage_sha256`, and `candidate.source_bundle_preimage_sha256`. It also binds `base.program_blob_oid`, `candidate.program_blob_oid`, `base.program_bytes_sha256`, and `candidate.program_bytes_sha256`, where each PROGRAM digest is recomputed over the exact extracted raw bytes. Missing, changed, omitted, added, reordered, mode/type-mutated, truncated, mismatched, or digest-aliased bytes produce PI_SOURCE_BINDING at the first exact entry or binding path in phase `source_bundle` with exit status 14.

## 8. Sole stable-promotion writer audit

F-07 remains the only stable-promotion authority. The future F-07 seam consists of `src/release/stable_store.py`, which defines the single low-level function `copy_immutable_digest_to_channel`, and `src/release/f07_promotion.py`, which is the only permitted caller. The sink accepts a verified `TrustedF07PromotionReceipt`, accepts only the literal channel `stable`, performs the atomic digest copy, and never computes closure or accepts a status override. The workflow and validator never write a channel.

The supported source language is Python 3.13 source parsed with the CPython 3.13 PEG grammar and `ast.parse(..., feature_version=(3, 13), type_comments=False)` from exact UTF-8 bytes. No generated language-neutral IR exists. Only regular 100644 `.py` entries under the exact Git-tracked `src/release/**` scope are supported. Any non-Python entry, including a `.py`-looking path with another type or mode, is categorically rejected as PI_STABLE_WRITER_LANGUAGE_UNSUPPORTED at `source.manifest.entries[0]` for the first-entry fixture and the actual indexed renderer otherwise, in phase `stable_writer` with exit status 12; there is no undeclared language-specific audit.

The audit accepts only the following AST node families: `Module`, `Import`, `ImportFrom`, `alias`, `FunctionDef`, `arguments`, `arg`, `Return`, `Assign`, `AnnAssign`, `Name`, `Load`, `Store`, `Attribute`, `Call`, `keyword`, `Constant`, `If`, `For`, `While`, `Try`, `ExceptHandler`, `Raise`, `With`, `withitem`, `Assert`, `Expr`, `Pass`, `BinOp`, `UnaryOp`, `BoolOp`, `Compare`, `IfExp`, `Dict`, `List`, `Tuple`, and their operator/comparator nodes. Each use is checked against exact arity, scope, and value rules. `AsyncFunctionDef`, `Await`, `AsyncFor`, `AsyncWith`, `Yield`, `YieldFrom`, `GeneratorExp`, `ListComp`, `SetComp`, `DictComp`, `Lambda`, `Match`, `NamedExpr`, `Global`, `Nonlocal`, `ClassDef`, decorators, type comments, f-string construction of sink arguments, and any unknown node are PI_STABLE_WRITER_UNSUPPORTED at the exact AST path in phase `stable_writer` with exit status 12.

The only permitted sink definition is a module-level function named `copy_immutable_digest_to_channel` in `release.stable_store`, with a fixed three-argument signature `(channel, digest, receipt)` and a return annotation of `None`. The only permitted receipt authority is the exact imported type `TrustedF07PromotionReceipt` and the exact constructor/authenticator `F07PromotionReceipt.authenticate`; an authenticated value must be assigned to a local named `receipt` and have the exact trusted type. The only allowed imports relevant to the seam are `from release.stable_store import copy_immutable_digest_to_channel`, `import release.stable_store`, and `from release.f07_promotion import F07PromotionReceipt, TrustedF07PromotionReceipt`, each optionally using one explicit `as NAME` alias that is resolved immediately to its canonical symbol. Wildcard, relative, import-time execution, `__import__`, `importlib`, `getattr`, string lookup, and dynamic import are rejected. A resolved alias cannot hide a second writer; every alias call is included in the sink count and evidence.

The call graph is built from module-qualified definitions and the three allowed import forms. Local function calls resolve by lexical scope and module identity; an unresolved call, indirect callable, reflection, `eval`, `exec`, shell execution, subprocess, network primitive, or dynamic attribute used on a sink path is rejected. Recursion or a call-graph cycle is rejected as PI_STABLE_WRITER_RECURSION; an acyclic graph deeper than 64 calls is PI_STABLE_WRITER_DEPTH. The audit follows wrappers interprocedurally and records every caller and call edge. Copied or generated source is still audited from its exact bytes and cannot be trusted by filename or comment.

The stable-channel primitive set is closed: the exact sink call, direct filesystem writes (`open` with a write mode), `Path.write_bytes`, `Path.write_text`, `os.replace`, `os.rename`, `shutil.copyfile`, `shutil.move`, subprocess execution, and network calls are all examined for a stable destination or stable-channel argument. Only the sink body may perform the approved atomic copy, and only the one caller may invoke the sink. A second definition, direct sink call, alias call, wrapper path, forbidden primitive, dynamic lookup, or stable destination in any other in-scope file is PI_SECOND_STABLE_WRITER at `policy.stable_writer.callers` in phase `stable_writer` with exit status 12.

The CFG has explicit entry, normal, exceptional, loop-back, break, continue, and return edges. Every expression that may raise has conservative edges to each enclosing exception handler. Standard dominance is computed over all reachable edges. The one sink call must be dominated on every path by `F07PromotionReceipt.authenticate` producing a `TrustedF07PromotionReceipt`; authentication inside only one branch, loop, exception path, or wrapper does not dominate a later sink. A sink in a handler, `finally`, loop, or recursive path must independently satisfy dominance. The first argument must be the literal constant `stable`; a variable, concatenation, environment value, enum, or equivalent spelling fails. Unknown constructs, unknown call targets, unsupported control flow, unresolved aliases, and incomplete CFG construction fail closed as PI_STABLE_WRITER_UNSUPPORTED, never PASS.

If either reserved seam file, the sink definition, the one allowed caller, or the trusted receipt definition is absent, the audit returns PI_STABLE_WRITER_SEAM_ABSENT at the exact missing path in phase `stable_writer` with exit status 12. Its JSON evidence includes seam status, source manifest and bundle digests, supported language/version, parsed modules, AST node census, import map, call graph, CFG hash, dominance witness, sink count, receipt type, and all rejected constructs.

## 9. Append-only history contract

The history parser selects exactly one structural raw heading `## 18. Decision log` and exactly one structural raw heading `## 19. Append-only progress log` in each input, with no trailing spaces. Each heading starts its region, which ends immediately before the next exact structural `## ` heading. Section 18 contains exactly one selected table beginning at the exact header `| Date | Decision | Reason |` and one exact delimiter row with exactly four ASCII pipe delimiters and three cells each containing exactly `---`; Section 19 uses the same rule with exact header `| Timestamp | Event | Evidence or result |`. Each region contains exactly one selected header and delimiter pair, and every history data row is one physical line with the exact four-delimiter table shape for its three columns. A duplicate heading, duplicate header, duplicate delimiter row, table-like line outside the selected table, or malformed lookalike is PI_HISTORY_REWRITE at `history.section18` or `history.section19` in phase `history` with exit status 13. Fence, comment, code-span, rendered, or HTML text cannot create or hide a region.

History row identity is the raw byte sequence of the complete physical table row including its exact LF terminator, or including no terminator when it is the final line. No trimming, decoding-and-encoding, Markdown parsing, or field normalization occurs before comparison. The base and candidate sequences are compared by exact zero-based index; rendered paths are `history.section18.rows[0]` and `history.section19.rows[0]` for the first-row fixture, with the same renderer substituting the actual shortest decimal index for generated fixtures. A duplicate-row detail uses both ordered indexes and never an ambiguous semantic key.

Acceptance requires the candidate sequence to have at least the base length and `candidate[i] == base[i]` for every base index. First, a candidate shorter than the base, or any candidate whose raw-row multiset lacks any base row with its full multiplicity, is PI_HISTORY_DELETE. Second, a same-length candidate with the same raw-row multiset but any row at a different index is PI_HISTORY_REORDER. Third, an exact base prefix permits only complete new rows after that prefix, and an appended duplicate is checked after the prefix test. Every remaining non-prefix mutation is PI_HISTORY_REWRITE. An insert in the middle, reorder-then-append, or append-then-rotate is PI_HISTORY_REWRITE. A pure same-length permutation is PI_HISTORY_REORDER. An appended exact raw duplicate is PI_HISTORY_DUPLICATE. These classifications are deterministic and total.

History errors report exact section, first differing zero-based index, one-based source line when available, base and candidate row counts, raw row digests, retained-prefix digest, and multiplicity evidence without echoing raw secrets. Sections 18 and 19 always use the actual immutable event base commit, never a branch name, a contributor-provided base file, or a symbolic merge ref. Policy-removal and authority-update records are valid only when their exact decision-log row bytes are appended after the retained base prefix.

## 10. Immutable Git-object trust and branch ancestry

All Git object access happens outside the isolated container in a trusted host adapter. The adapter obtains immutable event-bound commit SHAs, verifies exact 40-lowercase-hex syntax, verifies canonical repository ownership, resolves commit objects, and computes merge ancestry from those SHAs. It uses canonical GitHub pull-request refs `refs/pull/N/head` and `refs/pull/N/merge` only; N is the validated pull-request number, and it never fetches a contributor-fork URL, clone URL, arbitrary ref, or event-supplied remote.

For every base, candidate, merge, workflow, and source object, the adapter records and verifies commit OID, root tree OID, required blob OIDs, Git object type, byte length, and content SHA-256. It verifies each recorded tree equals its commit’s immutable root tree. It resolves each root-tree entry with `git ls-tree --full-tree -z`, verifies it with `git cat-file -t` and `git cat-file -s`, and extracts bytes only with `git cat-file blob <verified blob oid>`; it never reads PROGRAM.md through a candidate filesystem path. Base and candidate PROGRAM.md are root-tree entries whose exact path bytes are `PROGRAM.md`, exact type `blob`, and exact mode `100644`. A missing candidate entry is PI_PROGRAM_MISSING at `candidate.tree.PROGRAM.md` in phase `candidate_tree` with exit status 14. A symlink, submodule, traversal entry, unexpected slash, duplicate tree entry, wrong mode, or non-blob entry is PI_CANDIDATE_TREE_ENTRY at the exact entry path in phase `candidate_tree` with exit status 14.

The adapter extracts verified base and candidate PROGRAM blob bytes into fresh immutable input files named by logical role, not candidate paths. It extracts the bounded source scope into SourceManifest/v1 and SourceBundle/v1, and passes verified governance bytes. The container receives read-only mounts for those bytes, trusted validator source, and trusted tests only. It never receives a candidate checkout and never opens a candidate filesystem path named PROGRAM.md. The report binds every mounted byte to its commit/tree/blob OID and content digest.

The exact immutable validator roles are `base_program_bytes`, `candidate_program_bytes`, `base_commit_oid`, `base_tree_oid`, `base_program_blob_oid`, `candidate_commit_oid`, `candidate_tree_oid`, `candidate_program_blob_oid`, `merge_base_oid`, `candidate_source_manifest`, `candidate_source_bundle`, `event_json`, `governance_evidence`, and `report_json`. Symbolic base, head, candidate-root, candidate-program, or branch arguments do not exist. Every SHA role is a verified immutable object identity; every byte role has a recomputed SHA-256 preimage digest.

For a pull request, the typed event binding is canonical repository `omarchy-silicon/omarchy-apple-platform`, PR number N, event base `B = pull_request.base.sha`, canonical PR head `H = refs/pull/N/head`, merge candidate `C = refs/pull/N/merge`, and trusted base ref `refs/heads/main`. The trusted base ref must resolve to exactly B at verification time. The candidate commit must have exactly two parents in order `[B,H]`. The branch-up-to-date predicate is exact and mandatory: `git merge-base H B` must equal B, which proves B is an ancestor of H and therefore the PR head contains the required event base. Candidate-parent shape alone is insufficient. Failure of this predicate is PI_BRANCH_NOT_UP_TO_DATE at `event.pull_request.base.sha` in phase `trust` with exit status 14; an event/trusted-ref mismatch is PI_BRANCH_BASE_MOVED, and a candidate-parent/ref mismatch is PI_MERGE_CANDIDATE_STALE.

For a merge queue event, the binding is canonical repository, `merge_group.base_sha=B`, `merge_group.head_sha=H`, and `github.sha=C` as queue candidate. The adapter verifies candidate parent order, B is an ancestor of H when the queue contract requires the PR head, and H is an ancestor of C. It records queue identity and base/head/candidate state. For a push event, the binding is canonical repository, `after` or `github.sha=C`, and the first parent B; `before` must equal B for post-merge main verification. Any missing or inconsistent binding is PI_EVENT_UNSUPPORTED at `event` in phase `trust` with exit status 14.

The adapter recomputes all ref and ancestry evidence after each mutable GitHub/API read and immediately before report finalization. It re-resolves trusted base, canonical PR head, merge candidate, commit parents, root trees, and required check head SHA; any movement or disagreement invalidates the current evidence as PI_REF_MOVED at `trust.refs` in phase `trust` with exit status 14. It must then start a fresh event-bound run with the new immutable SHAs; a prior report, old candidate, or local branch cannot be reused. A merge queue candidate that moves or is regenerated is stale until all bindings and the ancestry predicate are recomputed.

Branch protection evidence must show strict required-status-check updates enabled for the protected `main` ref. The required-update rule is a boolean `strict=true` bound to the exact branch-protection rule ID, settings version, API response digest, and freshness record. Missing protection is PI_BRANCH_PROTECTION_MISSING; strict=false is PI_BRANCH_NOT_UP_TO_DATE; stale settings are PI_BRANCH_PROTECTION_STALE. A post-merge failure on main quarantines promotion, routes an owner incident, and requires a fresh successful verification at the new main SHA; rerun, warning text, or a stale report cannot remediate it.

The JSON report is a fixed `ProgramIntegrityReport/v1` schema. Its top-level keys are exactly `schema`, `result`, `primary`, `phases`, `fail_census`, `blocked`, `identities`, `authority`, `ledger`, `graph`, `policy`, `history`, `stable_writer`, `source`, `governance`, `invocation`, `fixtures`, `command`, and `exit_status`, serialized in that listed order. Unknown keys are forbidden. Every object’s keys are in the schema order declared for that object; every array has an explicit order: phases use `trust`, `authority`, `preflight`, `ledger_parse`, `graph`, `status`, `policy`, `promotion`, `history`, `stable_writer`, `source_bundle`, `workflow_trust`, `execution`, `fixtures`, `report`; failures use global precedence then path bytes; rows and entries use source/index or manifest order; IDs, status lists, item IDs, consumers, and paths use ascending ASCII or raw-byte order as named.

JSON bytes are UTF-8 with no BOM, no whitespace outside tokens, `ensure_ascii=true`, separators `,` and `:`, lowercase `true`, `false`, and `null`, integers only in shortest decimal form with no leading zero, and strings escaped with the RFC 8259 JSON escape set and lowercase four-digit `\u` hex. The final report has exactly one LF. `detail` is a string, never a free-form object. A failure record is exactly `{code, phase, path, detail, line, row_index, evidence}` where line is a one-based integer or null, row_index is a zero-based integer or null, and evidence is an ordered array of `{name, value, sha256}` records. A phase record is exactly `{name, state, blocked_by, failures}`. The fail census is an ordered array of failure records, not a count-only summary. Credentials, raw environment, source bytes, reason bytes, and signatures are redacted; their exact lengths and digests remain bound.

The canonical path renderer is byte-stable: for a zero-based integer `i`, `render_row(i)` emits `ledger.rows[` followed by the shortest ASCII decimal for `i` and then `]`; `render_field(i,name)` appends `.` and the fixed field name. A validated unique ID may instead use `ledger.rows["ID"].depends`, with ASCII double quotes and no escaping because the ID grammar is closed. The other exact renderers are `authority.section12_1.rows[i]`, `policy.diff.removed["ITEM_ID"]`, `policy.f07.direct_edges["ID"]`, `history.section18.rows[i]`, `history.section19.rows[i]`, `source.manifest.entries[i]`, `source.bundle.entries[i]`, `workflow.source`, `reviews[i]`, `check_runs[i]`, and `report.binding`, where each `i` is replaced by its shortest ASCII decimal before output. Before an ID is known or when duplicates exist, the indexed renderer is mandatory; no line-token placeholder is permitted.

PASS requires `result=PASS`, `exit_status=0`, PI_OK primary, every required phase PASS, zero failure records, zero blocked records, complete authority/source/governance/invocation evidence, exact current bindings, and no unavailable tool. FAIL requires `result=FAIL`, a primary code, exact phase/path/detail, all executed failure records, and explicit BLOCKED phase records. Warning is not a result or state. A nonempty fail census, warning-like text, missing evidence, stale binding, nonzero child status, or unavailable tool cannot coexist with PASS.

Human output is one deterministic line per failure in the form `FAIL code phase path detail` followed by one `BLOCKED phase blocked_by` line for each gated phase, using the same failure and phase order as JSON. It never labels a required failure as a warning and never prints PASS after a failure. A failed earlier phase controls all dependent phase states but independent history evidence may still be reported.
